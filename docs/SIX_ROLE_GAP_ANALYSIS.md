## 零、先講最重要的結構發現

這個 repo 裡住著**兩套獨立的系統**，而你的簡報畫的是**一條輸送帶**。

| | Next.js 儀表板 | Python Brand Intelligence OS |
|---|---|---|
| 角色 | Erick COO 指揮 Maya / Leon / Iris / Jack / Theo | discovery / scoring / decision / guardrail / learning |
| 觸發 | 人在對話框下指令 | `scripts/daily_run.sh` 每日排程 |
| 產出去向 | Supabase `insights_articles` ＋ n8n webhook | GitHub Pages ＋ Telegram |
| 資料庫 | Supabase / LocalStorage | SQLite (`database/orchestrator.db`) |

**互通性實測：Next.js 呼叫 Python 之處 0 個；Python 寫入 Supabase 之檔案 0 個。**

也就是說，你目前不是「六個抽屜」也不是「一條輸送帶」，而是**兩條各自運轉、彼此不知道對方存在的短輸送帶**。這是要做成圖中那條完整流水線之前，必須先解決的第一個問題。

## 一、逐站對照

### 01 AI 市場調研員 — 找到可用趨勢與題目
**判定：半成品，且未接前端**

Next.js 側**沒有**這個角色。Iris 常被誤認為調研，但她做的是「給定主題後擴充關鍵字」——輸入已經是題目了。DataForSEO 與 SEMrush 的串接（`ai-provider.ts:242-328`）是查詢**已知關鍵字**的搜尋量與競爭度，屬於驗證工具，不是發現工具。

Python 側有 `SourceDiscoveryEngine`，但 `discover_candidates()` 目前回傳的是**硬編碼的 mock 資料**（leanin.org、marieforleo.com 等），註解自己寫著 "Mock discovers"。

真正有價值的是 `data_acquisition.py`（2,197 行），裡面有實作的 `check_url()`、`clean_html()`、`extract_links()`、`verify_sources()`，是可運作的爬蟲與來源驗證。這塊是真的。

**缺口**：從「有爬蟲能力」到「自動產出今天值得寫的 5 個題目」之間，選題邏輯還是 mock。而且結果進不了前端。

---

### 02 AI 內容企劃員 — 把市場訊號變內容計畫
**判定：有，但輸入來源錯了**

`ERICK_SYSTEM_PROMPT` 定義的 Erick COO 就是這個角色，且做得相當完整：會把一句話拆解成 maya / leon / iris / jack 四份子提示詞，還有防禦性規則（標題被截斷要主動補全、使用者的細節要求禁止簡化抹除）。

但**它的輸入是人，不是市場訊號**。圖中這一站的定位是「把上游調研員找到的訊號，轉成內容計畫」；現況是「把老闆打的一句話，轉成四個子任務」。上游是空的。

Python 側的 `DecisionEngine.generate_recommendations()` 才是對應「從訊號產生建議」的角色，但同樣沒接前端。

**缺口**：訊號 → 選題 → 計畫這段的自動化。目前這段由你本人的大腦補完。

---

### 03 AI 品牌總編 — 守住觀點、語氣與紅線
**判定：已具備，且比圖中的描述更強**

這是整套系統裡最扎實的一塊，但分散在兩邊。

Next.js 側是**生成時的引導**：四個品牌各有 `*_BRAND_CONTEXT`，加上 `ERICK_PERSONA_SKILL` 語氣準則，注入到每次呼叫。

Python 側的 `BrandGuardrail` 是**產出後的檢查**，而且是可執行的硬規則：
- 分品牌禁用詞表（ABL 禁「療效/根治/治癒」、I8 禁「靈性/頻率/顯化/療癒」、NAS 禁「信息場/調頻/能量磁場」）
- 替換對照表（能量磁場→狀態、高票價→高價值、無痛成交→精準定位）
- 主題級改寫映射（正則比對整句，例如「如何透過⋯能量磁場⋯無痛成交⋯高票價⋯」直接改寫成「中年女性為什麼明明很努力，卻還是覺得狀態接不住？」）

這比圖裡「守住觀點、語氣與紅線」的抽象描述具體得多，已經是可稽核的合規層，對 ABL 這種涉及療效宣稱的品牌尤其重要。

**缺口**：`check_text()` / `rewrite_text()` **完全沒有接到 Next.js 的產出路徑上**。Maya 寫完文案直接進 Supabase 並可一鍵發布，中間沒有經過任何紅線檢查。這是目前**風險最高的一個缺口**——合規能力已經寫好了，但沒有掛上去。

---

### 04 AI 視覺企劃員 — 把內容變成可發布視覺
**判定：已具備，且明顯超出圖中設定**

這塊是意外的強項。

Maya 的提示詞（`ai-provider.ts:737-745`）會在文章適當段落插入 Markdown 圖片標籤，方括號內是給 DALL-E 3 的生圖描述，並有一套細緻規則：FB 宣傳圖強制為「真人寫實攝影」、明文禁止流程圖與插畫渲染、強制加入高度隨機的視覺細節（特定衣服顏色、背景小物、視角、光影時間）以避免每篇圖都長一樣。同時要求另外產出 Mermaid 流程圖供官網使用，**把 FB 的情境圖與官網的結構圖明確分流**。

Leon 則直接產出完整的響應式 Tailwind HTML Landing Page，含 Navbar、Hero、CTA 區，並依品牌套用配色（`getBrandColorsForPrompt`）。

**缺口**：實際生圖沒有串。圖片網址是 `https://filedn.com/your-id/...` 的佔位符，需要外部流程（推測是 n8n）去讀取描述、呼叫生圖 API、上傳到該路徑。這條鏈在程式碼裡是斷的。

---

### 05 AI 流量轉換企劃 — 把流量變成名單
**判定：頭尾都有，中間是空的**

**頭**有：Leon 的 Landing Page 會規劃 CTA 區塊，但轉換目標**硬編碼**成 `https://erickfirm.com/#contact`（`ai-provider.ts:898`）。

**尾**有：Jack 從 Meta Marketing API 抓 `last_30d` 的真實數據，會解析 `action_type === 'lead'` 算出 CPA 與 CVR（`ai-provider.ts:329-360`）。

**中間沒有**：沒有名單捕捉機制本身——沒有表單元件、沒有 email 自動化序列、沒有 CRM 串接、沒有 lead magnet 的產出邏輯。系統會「規劃一個 CTA 按鈕」也會「事後看名單成本」，但「把來的人變成名單」這段完全在系統外。

這是六站裡**缺口最大的一站**。

---

### 06 AI 數據復盤員 — 整理成效，提出下一輪假設
**判定：有「預測」沒有「復盤」；閉環在 Python 側但未啟用**

Theo（`callTheoAnalysis`）會給出 viral_score、reach_killers（指出哪句話會壓觸及）、以及逐句改寫建議，還特別處理了「忽略系統自動配圖的 Markdown 圖片連結，不可當作外連扣分」這種細節。但這是**發布前的預測**，不是發布後的復盤。

Jack 抓的是真實的 Meta 數據，但只是**展示**在 KPI 卡片上，不會回流到任何決策。

真正的閉環在 Python 側：`LearningEngine.process_analytics_feedback()` 會依 CTR 與 benchmark 的差距，動態調整品牌的 `score_weights`（opportunity / trend / roi），並寫回資料庫與 Feedback Event。

**缺口**：
1. 這個閉環沒接前端，且 benchmark 寫死 `2.0`，邏輯只處理 `delta > 0`（表現好才調整，表現差不調），實務上會單向偏移。
2. 「提出下一輪假設」這個動作，需要 `DecisionEngine` 與 `LearningEngine` 串起來，目前沒有。

## 二、工作流形態對照

**圖中**：調研 → 企劃 → 審核 → 視覺 → 轉換 → 復盤 →（回到調研）

**現況 Next.js**：
```
使用者下指令
  → Erick 拆解
  → 【第一條鏈】Iris 產關鍵字 → Maya 吃 Iris 的關鍵字寫文案
  → 【第二條鏈】Leon 吃 Iris+Maya 的產出做 Landing Page → Jack 做廣告數據
  → Theo（可選，手動觸發）
```

值得肯定的是：**你已經有「鏈」了，不是六個抽屜。** Maya 確實吃 Iris 的上游產出，Leon 確實吃 Iris 與 Maya 的產出，這正是簡報第二張圖要的「每一站有交付標準」。這比多數人的做法好。

**差別在於**：現況是一條**開放的線**（人下指令 → 產出 → 結束），圖中要的是**閉環的輸送帶**（復盤結果回饋成下一輪調研的輸入）。缺的是頭（調研）跟尾（復盤回饋），以及中間漏掉的審核站。

## 四、建議的優先順序

排序依據是「風險 × 成本」，不是依照輸送帶的順序。

**第一優先｜把 Guardrail 掛上產出路徑**
合規能力已經寫好了，卻沒有掛上去。ABL 品牌的禁用詞包含「療效、根治、治癒」，這在台灣是會觸法的用詞，而目前 Maya 產出的文案可以完全繞過檢查直接一鍵發布。這是**已完成的資產沒有生效**，投入最小、風險消除最大。

**第二優先｜補上 05 名單捕捉**
六站裡唯一真正空白的一站，且直接關係到營收。其他站產出的內容再好，流量沒有轉成名單就斷在這裡。

**第三優先｜串接生圖**
視覺規劃的品質已經很高，只差最後一哩。串起來就能從「文案 + 生圖描述」變成「可直接發布的貼文」。

**第四優先｜決定兩套系統的關係**
在做 01 調研與 06 復盤之前，必須先決定 Python 那套是要接進來、還是要獨立運作。這兩站的能力都在 Python 側，不解決互通問題就會重複造輪子。

## 五、動工前需要先回答的問題

1. **Python 那套 Brand Intelligence OS 是你在用的嗎？** 它每天自動 commit 一次（`chore: auto-publish daily dashboard`），代表排程還活著。但它跟儀表板零互通——這是刻意的分工，還是兩條線各自長出來的結果？

2. **名單要落在哪裡？** 這決定 05 怎麼做。是既有的 CRM、email 服務（Klaviyo/ConvertKit）、Google Sheet、還是 Supabase 自建？

3. **生圖要用哪個服務？** 提示詞是為 DALL-E 3 寫的，圖片路徑是 filedn.com。目前是靠 n8n 補完嗎？

4. **`erickfirm.com/#contact` 是唯一的轉換目標嗎？** 目前硬編碼在 Leon 的提示詞裡，若不同品牌要導到不同落地頁，這需要改成可設定。
